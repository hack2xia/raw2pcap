# raw2pcap

**English** | [简体中文](README.zh-CN.md)

**HTTP/1.x only.** raw2pcap creates pcap files from raw HTTP/1.x
request/response text. Paste (or point it at) a raw HTTP request and
optionally a response, and it synthesizes a complete TCP session in
memory — handshake, MSS-sized segments with ACKs, four-way close, valid
checksums — so the capture behaves like real traffic under Wireshark's TCP
reassembly, Follow Stream, and checksum validation.

## Usage

### Web UI

```bash
raw2pcap serve
```

`serve` binds to `127.0.0.1` by default and the API has no authentication, so
keep it on localhost unless you add your own protection (see
[Security](#security)).

Open the page, paste the request (required) and response (optional, a canned
`200 OK` with body `generated by raw2pcap` is used when empty), optionally
set the Client IP / Server IP used in the synthesized session (defaults
`10.10.10.1` / `10.10.10.2`), pick a filename, and download the pcap.

The same endpoint is available programmatically:

```bash
curl -o out.pcap -F 'inputRequest=@request.txt' -F 'inputResponse=@response.txt' \
  -F 'clientIp=10.0.0.2' -F 'serverIp=192.168.1.10' \
  http://localhost:5000/api/pcap
```

### CLI

```bash
raw2pcap generate request.txt [response.txt] -o out.pcap
```

Customize the addresses used in the synthesized session with
`--client-ip` / `--server-ip` (defaults `10.10.10.1` / `10.10.10.2`):

```bash
raw2pcap generate request.txt response.txt -o out.pcap \
  --client-ip 10.0.0.2 --server-ip 192.168.1.10
```

## Scope: not for bulk generation

**raw2pcap is designed for one-off, interactive capture synthesis — do not
use the web API for bulk pcap creation.** If you need many pcaps, write a
script that drives the CLI (or calls `raw2pcap.generate.generate_pcap`
directly) instead.

Reasons:

- Packet synthesis is pure-Python CPU-bound work. The web API runs it in
  worker threads that are serialized by the GIL, so concurrent requests do
  not speed anything up — they just all get slower.
- The HTTP layer itself is defensive, not scalable: request bodies are
  rejected above 256 KiB (413), and only 3 connections are handled
  concurrently (the rest queue).
- The Docker container is expected to run with tight resource limits
  (`--memory 512m --cpus 1 --pids-limit 100`).

## Guarantees

- **Input validation** (`validate.py`): malformed input is rejected with 400 —
  e.g. HTTP/1.1 requests without `Host`, a header/body separator line that
  starts with whitespace, obsolete folded headers, a `Host` port outside
  1–65535, non-numeric or duplicate `Content-Length`, or any
  `Transfer-Encoding: chunked` message (chunked bodies are not decoded; paste
  the decoded body with `Content-Length` instead). Suspicious-but-legal input
  (a single Content-Length that mismatches the body) produces warnings
  returned in the `X-Raw2pcap-Warnings` response header.
- **Output self-check** (`selfcheck.py`): every generated pcap is immediately
  re-parsed and verified — checksums recomputed, sequence numbers checked for
  gaps/overlaps, reassembled payloads compared byte-for-byte with the HTTP
  messages. A failure means a synthesizer bug and returns 500.

## Fidelity caveats

The captures are *synthetic by design* and will look like it to a trained
eye: TCP options (SACK, timestamps, MSS negotiation) are absent, the window
size is fixed (64240), ISNs are fixed (1000/5000), and inter-packet delays
are a mechanical 0.1 ms. The sessions are perfect — no retransmissions, no
jitter — which real traffic never is. This is fine for IDS rule testing,
parser development, and teaching; do not expect these pcaps to pass as
genuinely captured traffic under close inspection. Sessions are synthesized
over IPv4 only; IPv6 is not supported.

## Configuration

Deployment-time knobs, set as environment variables (read once at startup):

| Variable | Default | Effect |
|---|---|---|
| `RAW2PCAP_MAX_BODY_BYTES` | `262144` (256 KiB) | Max combined request+response size accepted by the API (413 above) |
| `RAW2PCAP_LIMIT_CONCURRENCY` | `3` | Concurrent connections admitted by uvicorn; the rest queue |
| `RAW2PCAP_MSS` | `1460` | TCP segment size used when splitting payloads into packets |

## Security

The web API has **no authentication**. Each request can burn roughly 2.3
seconds of CPU at the 256 KiB size limit, with up to 3 requests admitted
concurrently — anyone who can reach the endpoint can keep all cores busy.

`raw2pcap serve` binds to `127.0.0.1` by default — keep it that way and do
**not expose the service to untrusted networks**. If you must make it
reachable, put it behind a reverse proxy that adds authentication and enforce
resource limits (the Docker command below uses
`--memory 512m --cpus 1 --pids-limit 100`).

## Development

```bash
uv sync
uv run pytest              # tests
uv run ruff check .        # lint
```

Docker:

```bash
docker build -t raw2pcap:latest .
docker run -d -p 5000:5000 --memory 512m --cpus 1 --pids-limit 100 \
  --restart unless-stopped raw2pcap:latest
```

If port 5000 is already taken on the host — on macOS the AirPlay Receiver
frequently occupies it, returning a 403 from `AirTunes` — map a different
host port instead:

```bash
docker run -d -p 5001:5000 --memory 512m --cpus 1 --pids-limit 100 \
  --restart unless-stopped raw2pcap:latest
```
